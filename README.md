## Part B

**1.** ผลการทดสอบ A1-A5 แสดงในตาราง Part A 

**2.** แต่ละ VU ต้องรอ `sleep(1)` ก่อนเริ่มรอบถัดไป จึงไม่ได้ส่ง requests
ต่อเนื่องตลอดเวลา อัตราที่วัดได้คือ 3.572235 req/s

**3.** ค่า p(95) เพิ่มจาก 375.89 ms ใน A2 เป็น 437.58 ms ใน A3 หรือเพิ่มขึ้น
61.69 ms โดย failed requests = 0.00% และ checks ผ่าน 100.00%
จึงยังไม่พบความล้มเหลวชัดเจนภายในช่วงที่ทดสอบ อย่างไรก็ตาม QuickPizza
เป็นเว็บไซต์สาธารณะที่ใช้ร่วมกัน และทดสอบได้สูงสุด 5 VUs
จึงยังบอกไม่ได้ว่าระบบจะทำงานอย่างไรเมื่อเกินขอบเขตการทำงานนี้ (operational
envelope)

**4.** หลังเกิด spike ใช้เวลาประมาณ 5 วินาทีที่ response time จะกลับมาใกล้ระดับเดิม

**5.** response time ช่วงต้นและช่วงท้ายอยู่ประมาณ 300--350 ms และ error rate =
0.00% จึงไม่พบว่าแย่ลงตามเวลา การทดสอบ soak test
ที่ใช้เวลาหลายชั่วโมงอาจตรวจพบปัญหา `memory leak`

**6.** ค่า average อาจซ่อน requests ที่ตอบสนองช้ามากได้ ส่วน p(95) แสดงเวลาที่
95% ของ requests ตอบกลับได้ภายในค่านั้น
จึงช่วยให้เห็นปัญหาการตอบสนองที่ช้าได้ชัดเจนกว่าใช้ average อย่างเดียว

**7.** ผลทดสอบใน Lab อาจแตกต่างกันได้จาก 2 สาเหตุ: -
ความหน่วงของเครือข่าย การกำหนดเส้นทาง (routing) และความแออัดของเครือข่าย
(network congestion) ต่างกัน -
จำนวนผู้ใช้และภาระงานของระบบในช่วงเวลาที่ทดสอบต่างกัน

**8.** การส่ง requests จำนวนหลายร้อย users
ไปยังเว็บไซต์ที่เราไม่ได้เป็นเจ้าของอาจทำให้ระบบช้าหรือไม่สามารถให้บริการได้
และกระทบผู้ใช้อื่น จึงต้องทดสอบเฉพาะระบบที่ได้รับอนุญาต โดย Lab นี้จำกัด QuickPizza
ไว้ไม่เกิน 5 VUs
